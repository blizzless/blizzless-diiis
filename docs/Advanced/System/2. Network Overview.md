# Game Server Connection Flow

## Executive Summary

This technical article analyzes the connection flow in the **DiIiS-NA** Diablo III server rework by examining the provided server logs and correlating them with the actual C# codebase. The logs reveal a sophisticated multi-stage connection architecture involving game server registration, client encryption, authentication, service binding, and presence management.

---

## Architecture Overview

The DiIiS-NA system employs a **three-tier architecture**:

```
┌──────────────────────────────────────────────────────────────────┐
│  TIER 1: Game Server (D3-GameServer)                              │
│  - Listens on port 2001                                           │
│  - Accepts game clients (GameClient connections)                  │
│  - Registers with Battle Backend                                  │
└──────────────────────────────────────────────────────────────────┘
                           ↑↓ TCP
┌──────────────────────────────────────────────────────────────────┐
│  TIER 2: Battle Backend (BGS-Server)                              │
│  - Manages server registry (GameServers dictionary)               │
│  - Routes authentication and presence services                    │
│  - Maintains persistent connections with game servers             │
└──────────────────────────────────────────────────────────────────┘
                           ↑↓ TCP
┌──────────────────────────────────────────────────────────────────┐
│  TIER 3: Game Client (Diablo III Client)                          │
│  - Establishes encrypted connection to Battle Backend             │
│  - Authenticates via AuthenticationService                        │
│  - Subscribes to services (Presence, Friend, Channel, etc.)       │
└──────────────────────────────────────────────────────────────────┘
```

```csharp
// BattleBackend.cs - Battle Backend side
private bool ReceiverMessageReceived(string ipPort, byte[] data)
{
    string msg = "";
    if (data != null && data.Length > 0) 
        msg = Encoding.UTF8.GetString(data);
    Logger.Trace("Message received from $[grey69]${0}$[/]$: $[white]${1}$[/]$", ipPort, msg);
    
    var message = msg.Split(new[] { '|' }, StringSplitOptions.RemoveEmptyEntries);
    var args = message[1].Split(new[] { '/' }, StringSplitOptions.RemoveEmptyEntries);
    
    switch (message[0])
    {
        case "rngsr":  // Register Game Server Request
            if (GameServers.ContainsKey(ipPort)) GameServers.Remove(ipPort);
            string rgsIp = args[0];
            int rgsPort = int.Parse(args[1].Trim());
            GameServers.Add(ipPort, new ServerDescriptor { GameIp = rgsIp, GamePort = rgsPort });
            break;
    }
}
```

### Protocol Details

**Message Format:** `rngsr|{GameServerIP}/{GameServerPort}`

| Component | Value | Purpose |
|-----------|-------|---------|
| Command | `rngsr` | Register Game Server Request |
| GameServerIP | `127.0.0.1` | Public/accessible game server IP |
| GameServerPort | `2001` | Game server listening port |
| Connection | TCP from port 58624 | Game server initiates connection |

### Data Structure

```csharp
public struct ServerDescriptor
{
    public string GameIp;      // 127.0.0.1
    public int GamePort;       // 2001
}

public readonly Dictionary<string, ServerDescriptor> GameServers = new();
// Key: "127.0.0.1:58624" (Game server connection endpoint)
// Value: ServerDescriptor { GameIp: "127.0.0.1", GamePort: 2001 }
```

**Result:** Battle Backend now knows where to route game-creation requests. The GameServers dictionary stores the mapping between:
- The TCP connection through which the game server connected (58624)
- The actual game server's public address and port (127.0.0.1:2001)

```csharp
[Service(serviceID: 0xb, serviceName: "bnet.protocol.presence.PresenceService")]
public class PresenceService : bgs.protocol.presence.v1.PresenceService, IServerService
{
    public override void BatchSubscribe(IRpcController controller, BatchSubscribeRequest request, 
                                      Action<BatchSubscribeResponse> done)
    {
        var response = BatchSubscribeResponse.CreateBuilder();
        
        foreach (var req in request.EntityIdList)
        {
            switch (req.GetHighIdType())
            {
                case EntityIdHelper.HighIdType.AccountId:
                {
                    var account = AccountManager.GetAccountByPersistentID(req.Low);
                    if (account != null)
                    {
                        Logger.MethodTrace($"{(((HandlerController)controller).Client)} {account}");
                        // Line 124: Subscribe to Account entity
                        account.AddSubscriber((((HandlerController)controller).Client), request.ObjectId);
                    }
                }
                break;
                
                case EntityIdHelper.HighIdType.GameAccountId:
                {
                    var gameAccount = GameAccountManager.GetAccountByPersistentID(req.Low);
                    if (gameAccount != null)
                    {
                        Logger.MethodTrace($"{(((HandlerController)controller).Client)} {gameAccount}");
                        // Line 134: Subscribe to GameAccount entity
                        gameAccount.AddSubscriber((((HandlerController)controller).Client), request.ObjectId);
                    }
                }
                break;
            }
        }
        
        done(response.Build());
    }
    
    public override void Update(UpdateRequest request, Action<NoData> done)
    {
        // Line 220: Called whenever presence changes
        Logger.MethodTrace($"Update(): {client} - {operationCount} Operations {program}, {originatingClass}, {fieldId}");
        done(NoData.CreateBuilder().Build());
    }
}
```

```csharp
private bool ReceiverClientDisconnected(string ipPort)

    Logger.Warn("Blizzless client disconnected $[white]${0}$[/]$!", ipPort);
    if (GameServers.ContainsKey(ipPort)) 
        GameServers.Remove(ipPort);
```

## Security Considerations Evident from Logs

1. **Encryption Required**: Every client connection undergoes SSL/TLS before RPC
2. **Version Validation**: Client version checked during authentication (87562 vs accepted versions)
3. **Platform Detection**: Platform field ("Wn64") tracked for client validation
4. **Entity ID Separation**: Account (lowId: 5) and GameAccount (lowId: 5) kept separate
5. **Service-Level Authentication**: Each service checks BattleClient authentication status
6. **Subscriber Isolation**: Presence updates only sent to subscribed clients

The DiIiS-NA Diablo III server rework implements a sophisticated RPC-based connection flow:

1. **Game servers** register themselves with the Battle Backend via simple text protocol
2. **Game clients** establish SSL/TLS encrypted connections
3. **Services** are bound and exposed via the RPC channel
4. **Authentication** validates credentials and version compatibility
5. **Subscriptions** establish bidirectional presence and state synchronization
6. **Multiple parallel connections** are managed independently per client

The logging output reveals a well-instrumented system with clear separation of concerns between connection management (DotNetty), authentication (AuthenticationService), and real-time updates (PresenceService). The architecture scales by maintaining per-connection state and allowing multiple simultaneous BattleClient instances.

For developers implementing similar systems, the key lessons are:
- Use immutable message protocols (Protocol Buffers) for RPC definitions
- Implement service-based architecture for loose coupling
- Maintain clear logging at Trace/Info/MethodTrace levels for debugging
- Separate concerns: connection, authentication, and application services
- Use thread-safe collections for multi-client state management
