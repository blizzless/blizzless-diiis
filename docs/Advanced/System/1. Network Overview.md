## Introduction

Establishing and maintaining a connection between a game client and a game server is a complex, multi-layered process that involves network protocols, authentication mechanisms, packet structures, and state management. This article provides a comprehensive technical overview of how these connections are established, with particular attention to Blizzard game protocols and architectures relevant to games like Diablo III.

We'll start from the basics.

## Part 1: Transport Layer Fundamentals

### TCP vs. UDP: Protocol Selection

The choice between TCP and UDP fundamentally shapes the connection flow:

**TCP (Transmission Control Protocol):**[[1]](https://www.gafferongames.com/post/client_server_connection/)[[3]](https://www.geeksforgeeks.org/computer-networks/tcp-and-udp-in-transport-layer/)
- **Characteristics**: Reliable, ordered, connection-oriented
- **Use Cases**: Authentication, login, character data synchronization, persistent sessions
- **Overhead**: Higher latency, more bandwidth overhead due to acknowledgments
- **Guarantee**: Every packet delivered in order

**UDP (User Datagram Protocol):**[[1]](https://www.gafferongames.com/post/client_server_connection/)[[6]](https://bytebytego.com/guides/what-protocol-does-online-gaming-use-to-transmit-data/)
- **Characteristics**: Fast, connectionless, unreliable
- **Use Cases**: Real-time gameplay data (positions, actions, chat in fast-paced games)
- **Overhead**: Minimal latency, low bandwidth consumption
- **Trade-off**: Packets may be lost or arrive out-of-order; developers implement custom reliability (RUDP) when needed

Most modern games use a **hybrid approach**:
- **TCP** for critical control channels (login, inventory, trading, character data)
- **UDP** for time-sensitive gameplay data (positions, animations, projectiles)

## Part 2: The TCP 3-Way Handshake

When using TCP for game connections, the session begins with the standardized TCP 3-Way Handshake:[[3]](https://wiki.wireshark.org/TCP_3_way_handshaking)[[4]](https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/three-way-handshake-via-tcpip)[[5]](https://www.geeksforgeeks.org/computer-networks/tcp-3-way-handshake-process/)

### Handshake Sequence

```
Step 1: SYN (Client → Server)
├─ Client initiates connection
├─ Sequence number: x (arbitrary)
├─ Flags: SYN
└─ Payload: Empty

Step 2: SYN-ACK (Server → Client)
├─ Server acknowledges client's SYN
├─ Sequence number: y (arbitrary)
├─ Acknowledgment number: x + 1
├─ Flags: SYN + ACK
└─ Payload: Empty (or server parameters)

Step 3: ACK (Client → Server)
├─ Client confirms receipt of server's SYN
├─ Sequence number: x + 1
├─ Acknowledgment number: y + 1
├─ Flags: ACK
└─ Payload: First application data (optional)
```

### Network Sequence Diagram

```
Client                              Server
  |                                   |
  |--------- SYN (seq=x) ------------>|
  |                                   |
  |<------ SYN-ACK (seq=y, ack=x+1) --|
  |                                   |
  |-------- ACK (seq=x+1, ack=y+1) -->|
  |                                   |
  |---- [Connection Established] ---->|
  |                                   |
  |<--- Application Data Exchange --->|
```

**Key Points**:[[7]](https://www.guru99.com/tcp-3-way-handshake.html)
- Both client and server agree on initial sequence numbers
- The connection is now in the ESTABLISHED state
- Either side can begin sending application layer data
- This handshake itself takes a round-trip time (RTT) of typically 50-200ms depending on network latency

## Part 3: UDP and Custom Game Protocol Handshakes

For games prioritizing speed over reliability, UDP requires a custom handshake:[[1]](https://www.gafferongames.com/post/client_server_connection/)[[8]](https://github-wiki-see.page/m/Xsear/Documentation/wiki/Game-Server-Protocol-Overview)

### Custom UDP Connection Flow

```
Step 1: Client Connection Request
├─ Client sends UDP packet with connection intent
├─ Includes: client version, nonce, optional authentication token
└─ Server may validate IP/port pair

Step 2: Server Challenge/Token Response
├─ Server sends connection token or challenge
├─ Includes: session ID, server configuration, encryption key seed
└─ Optional: CAPTCHA or anti-DDoS verification

Step 3: Client Confirmation
├─ Client acknowledges token/challenge
├─ Includes: token response, confirmation of settings
└─ Connection is now ready for game traffic

Step 4: Heartbeat/Keep-Alive
├─ Periodic messages maintain connection state
├─ Detect disconnections or timeouts
└─ Typically sent every 5-30 seconds
```

This custom handshake is lighter than TCP's 3-way but still provides basic flow control and client validation, helping mitigate DDoS attacks by requiring multiple round-trips before allocating significant server resources.

## Part 4: Blizzard Battle.net Protocol

Blizzard games employ sophisticated protocol layers. Here's the connection flow for Battle.net-based games:[[1]](https://bnetdocs.org/document/16/protocol-headers)[[2]](https://deepwiki.com/pvpgn/pvpgn-server/4.1-battle.net-protocol)

### Protocol Layers

```
┌─────────────────────────────────────────────────┐
│         Application Layer (Game Data)            │
│   (Character Data, Game State, Chat)             │
├─────────────────────────────────────────────────┤
│      Battle.net / Realm Protocol Layer           │
│   (Formatted Packets with IDs and Payloads)      │
├─────────────────────────────────────────────────┤
│    Transport Layer (TCP or UDP)                  │
│    (3-Way Handshake, Reliability)                │
├─────────────────────────────────────────────────┤
│    Network Layer (IP/IPv6)                       │
│    (Routing, Fragmentation)                      │
└─────────────────────────────────────────────────┘
```

### Blizzard Packet Structure

**BNCS (Battle.net Chat Server) Format:**[[1]](https://bnetdocs.org/document/16/protocol-headers)
```
Offset  Size   Type    Description
0       1      UINT8   Always 0xFF (Packet Signature)
1       1      UINT8   Message ID (identifies packet type)
2       2      UINT16  Message Length (includes header, little-endian)
4       N      BYTES   Message Data (payload)
```

**Realm Server Format:**
```
Offset  Size   Type    Description
0       2      UINT16  Message Length (little-endian)
2       1      UINT8   Message ID
3       N      BYTES   Message Data
```

**D2GS (Diablo II Game Server) Format:**
```
Offset  Size   Type    Description
0       1      UINT8   Message Length (if < 255)
        or 2           Message Length extended (if >= 255, 0xFF prefix)
1       1      UINT8   Message ID
2       N      BYTES   Message Data
```

### Example: Login Flow via Battle.net

```
Client                                    Battle.net Server
  |                                           |
  |-- TCP SYN -------------------------------->|
  |<----- TCP SYN-ACK -------------------------|
  |-- TCP ACK --------------------------------->|
  |                                           |
  |-- [0xFF, SID_LOGONRESPONSE, ...] ------->|
  |   (Send login credentials + version)     |
  |                                           |
  |<--- [0xFF, SID_LOGONRESPONSE, ...] ------|
  |    (Server returns result code)           |
  |                                           |
  | [If authenticated, continue to           |
  |  character selection/game join]          |
  |                                           |
```

### Phase 1: Server Discovery and Initial Connection

```
┌─────────────────────────────────────────────┐
│  1. Client retrieves server list            │
│     - Via hardcoded server addresses        │
│     - Via DNS lookup (battle.net domain)    │
│     - Via matchmaking/lobby service         │
└─────────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────────┐
│  2. Client initiates TCP or UDP connection  │
│     - Resolves IP address                   │
│     - Connects to standard port (e.g., 6112)│
└─────────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────────┐
│  3. Transport layer establishes socket      │
│     - TCP: 3-way handshake                  │
│     - UDP: Socket created, ready to send    │
└─────────────────────────────────────────────┘
```

### Phase 2: Authentication and Validation

```
┌─────────────────────────────────────────────┐
│  1. Client sends authentication packet      │
│     - Username/password hash                │
│     - Game version                          │
│     - Client version                        │
│     - Session token (if reconnecting)       │
└─────────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────────┐
│  2. Server validates credentials            │
│     - Queries user database                 │
│     - Checks version compatibility          │
│     - Verifies session token/IP             │
└─────────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────────┐
│  3. Server responds with status             │
│     - Success: Sends session token          │
│     - Failure: Sends error code             │
│     - (For Diablo III: Returns character    │
│       list, account state)                  │
└─────────────────────────────────────────────┘
```

### Phase 3: Game Lobby/Character Selection

```
┌─────────────────────────────────────────────┐
│  1. Client requests character list          │
│     - Packet: List characters owned by user │
└─────────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────────┐
│  2. Server sends character data             │
│     - Character names, levels, classes      │

│     - Available games/lobbies               │

         ↓
```

```
┌─────────────────────────────────────────────┐
│  1. Client requests to join/create game     │

         ↓

         ↓
┌─────────────────────────────────────────────┐
│  3. Server sends world state initialization │

         ↓
┌─────────────────────────────────────────────┐
│  4. Client ready acknowledgment             │
│     - Client renders world                  │
│     - Sends ready packet                    │
└─────────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────────┐
│  5. Continuous gameplay communication       │
│     - Player movement, actions              │
│     - Monster updates                       │
│     - Chat and social packets               │
│     - Inventory changes                     │
└─────────────────────────────────────────────┘
```

## Part 6: Packet Class Hierarchy and Serialization

In C# (relevant to your Diablo III server rework), packets are typically modeled as classes with serialization:[[1]](https://bnetdocs.org/document/16/protocol-headers  and https://inet.omnetpp.org/docs/developers-guide/ch-packets.html)

### Example Class Structure

```csharp
// Base packet class
public abstract class BattleNetPacket
{
    public byte PacketType { get; protected set; }
    public ushort Length { get; set; }
    
    public abstract byte[] Serialize();
    public abstract void Deserialize(byte[] data);
}

// BNCS login packet (client → server)
public class LogonPacket : BattleNetPacket
{
    public byte[] ClientToken { get; set; }  // 4 bytes
    public uint VersionByte { get; set; }     // 4 bytes, game version
    public string Username { get; set; }      // null-terminated string
    public string PasswordHash { get; set; }  // null-terminated string
    
    public override byte[] Serialize()
    {
        var buffer = new List<byte>();
        buffer.Add(0xFF);                          // Signature
        buffer.Add(0x00);                          // SID_LOGON
        // ... serialize other fields
        ushort length = (ushort)buffer.Count;
        // Insert length at offset 2-3
        return buffer.ToArray();
    }
    
    public override void Deserialize(byte[] data)
    {
        // Parse incoming packet data
    }
}

// Game world update packet (server → client)
public class PlayerUpdatePacket : BattleNetPacket
{
    public uint PlayerId { get; set; }
    public float X { get; set; }
    public float Y { get; set; }
    public uint AnimationState { get; set; }
    
    public override byte[] Serialize() { /* ... */ }
    public override void Deserialize(byte[] data) { /* ... */ }
}
```

### Serialization Considerations

1. **Endianness**: Battle.net protocols typically use **little-endian** byte order
2. **Alignment**: Respect padding requirements (commonly 4-byte alignment)
3. **Null Termination**: Strings are often null-terminated in legacy Blizzard protocols
4. **Variable-Length Data**: Use length prefixes for dynamic arrays
5. **Checksum/Validation**: Include CRC32 or similar for data integrity

## Part 8: Security and DDoS Mitigation

### Threats in Game Connection Flows

1. **Spoofed Connection Requests**: Attackers send fake packets to exhaust resources
2. **Credential Brute Force**: Attackers attempt multiple login combinations
3. **DDoS Amplification**: Attacker-controlled clients flood server with requests
4. **Man-in-the-Middle (MITM)**: Interception of unencrypted packets

### Mitigation Strategies

```
┌─────────────────────────────────────────────┐
│  1. Connection Rate Limiting                 │
│     - Max connections per IP: 5              │
│     - Backoff period: 60 seconds             │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│  2. Early Validation                         │
│     - Verify packet signature (0xFF)         │
│     - Check message length                   │
│     - Validate version compatibility         │
│     - Only allocate resources AFTER auth     │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│  3. Encryption                               │
│     - TLS/SSL for critical sessions          │
│     - Encrypt sensitive packets              │
│     - Use session tokens instead of          │
│       passwords for reconnection             │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│  4. Heartbeat/Keep-Alive                     │
│     - Detect dead connections quickly        │
│     - Free stale resources                   │
│     - Challenge-response handshakes          │
└─────────────────────────────────────────────┘
```

## Conclusion

The connection flow in game servers is a carefully orchestrated sequence involving:

1. **Transport Layer** (TCP/UDP handshakes and reliability)
2. **Protocol Layer** (Blizzard's packet formats and message IDs)
3. **Application Layer** (Authentication, character selection, game world)
4. **State Management** (Tracking client connection states)
5. **Security** (Rate limiting, encryption, validation)

For your Diablo III server rework in C#, understanding these layers ensures:
- Robust authentication and session management
- Efficient packet serialization/deserialization
- Proper error handling and disconnection recovery
- Scalability for multiple concurrent connections
- Resilience against common network attacks
